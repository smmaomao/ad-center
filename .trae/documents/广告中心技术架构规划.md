# 广告中心（Ad Center）技术架构规划与实施计划

## Context

短剧 App 自有广告投放管理系统（内部使用），需求基线为 [docs/PRD.md](file:///Users/bereal-01/bereal/ad-center/docs/PRD.md)（V1.1，KPI 优先决策）。核心：管理甲方广告主/素材、KPI 优先的流量分配决策（对外 API）、实时监控看板、规则引擎版 AI Agent。

**已确认技术决策**：Go 后端 · Supabase（Postgres/Auth/Storage）+ Vercel 前端 · V1 规则引擎 · Flutter 客户端。
**硬指标**：决策接口平均 <100ms / P99 <200ms；配置秒级生效；看板延迟 <3s；日志 ≥180 天。

## 总体架构

```
Flutter App (Ad Center SDK + AppLovin MAX 兜底)
        │ HTTPS + HMAC 签名
        ▼
Go 单体服务（单实例，双端口）
  :8080 Open API   /api/v1/ads/request (<100ms) · /events/batch · /config/slots
  :8081 Admin API  CRUD / 看板 / AI Agent（Supabase JWT + RBAC）
  ── Decision Core（纯内存热路径，0 次 DB 同步往返）──
     ConfigCache(热更新) · BudgetCtrl(原子扣减) · FrequencyStore(LRU)
     ScoringEngine(KPI公式) · CreativeSelector(A/B) · RealtimeCounters
  ── 后台任务 ──
     EventIngest(批量落库) · RuleAgent(定时规则) · ConfigSync(NOTIFY+轮询)
        │                              │
        ▼                              ▼
  Supabase (SG region)          Vercel (Next.js 管理后台)
  Postgres · Auth · Storage      supabase-js 登录 · TanStack Query 3s 轮询
```

## 关键架构决策

1. **单 Go 二进制双端口**（非两个服务）：决策热路径依赖进程内状态，管理端保存配置后直接触发内存缓存 Reload，毫秒级生效，无跨进程通信。代码内部分包（`internal/decision`、`internal/api/open`、`internal/api/admin`），未来 QPS 增长可无痛拆出。
2. **不引入 Redis**：容量估算 DAU 50万 / 峰值 QPS 300~500，Go 单实例纯内存决策（单请求 CPU <0.1ms）绰绰有余。升级触发条件（QPS>3000 / 多活 / 跨实例频控一致）写入 runbook，BudgetCtrl/FrequencyStore 接口已隔离，届时迁 Redis 只改实现。
3. **配置秒级生效三通道**：同进程直通（主通道，Admin API 写库后直接 Reload）→ Postgres LISTEN/NOTIFY（旁路，覆盖 DBA 直改库场景，须用 session pooler 5432）→ 10s 版本轮询兜底（防 NOTIFY 断连漂移）。
4. **预算扣减**：进程内 `sync.Map + atomic` 扣减（决策立即可见，防超发）→ 2s/500 条异步批量落库（UPSERT `advertiser_daily_stats` + INSERT `budget_ledger`）；崩溃重启从每日快照恢复，误差 ≤2s 窗口。**CPI/CPA 在转化事件到达时真实扣费**；曝光仅累计预估消耗（imps × effectiveEcpm/1000）供决策与看板参考。
5. **频控/疲劳度**：进程内 LRU（上限 100 万用户条目 ≈300MB，超出淘汰最久未活跃），业务日按 Asia/Jakarta（UTC+7）切日，DB 统一 UTC timestamptz。重启丢失 = 用户当日多看几次广告，业务可接受，不持久化。
6. **看板 <3s**：数据源即决策进程内存计数器，前端 TanStack Query 3s 轮询 Admin API（内部工具并发 <20 人，压力可忽略）；Supabase Realtime 留作 P2 推送增强。
7. **数据保留分级**（修正 PRD 字面"全量 180 天"，8 亿行不可行）：转化明细（计费依据）/决策日志/审计日志 ≥180 天；曝光点击明细 30 天 + 小时聚合 2 年；请求明细 5% 采样 + no_fill 全量，保留 30 天。
8. **决策公式**（乘数全部参数化，存 `decision_params`，可运营调整）：
```
finalScore = urgency × budgetProgress × tierWeight × kpiGuard × pace
  urgency        = 1 / (achievementRate + 0.01)
  budgetProgress = spentToday / dailyBudget
  tierWeight     = 1.5 / 1.2 / 1.0
  kpiGuard       = 达成率 > 0.85 ? 1.2 : 0.8
  pace           = 消耗进度 < 时间进度-10% ? 1.3 : 1.0
过滤: status=active ∧ 预算未耗尽 ∧ 频控未超 ∧ 定向匹配
排序遍历: 疲劳窗口内跳过 → 权重选素材 → 返回；无填充 → fallback max → house
```

## PRD 口径矛盾的定稿处理

PRD 存在两处矛盾，实现按下述口径（已写入代码注释与 API 文档，如产品后续确认不同再改参数）：

| 矛盾点 | 定稿口径 |
|--------|----------|
| KPI 达成率定义：FR-01 说"实际/目标，≤1 达标"，6.1/FR-08 说"目标/实际，≥100% 达标" | **采用 6.1/FR-08：达成率 = targetCpi/actualCpi，≥100% 达标**（信号更直观，预警阈值 85% 与之自洽） |
| 5.1 流程图中 KPI<85%（紧急）反而 ×0.8 降权，与"优先保障未达标广告主"矛盾 | **按"优先保障未达标"的业务本意实现：KPI<85% 提权（×1.2 甚至更高），乘数参数化**，5.1 图的 ×0.8 视为文档笔误 |

## 数据库（Supabase Postgres）

| 表 | 要点 |
|----|------|
| `profiles` | 后台用户角色（super_admin/operator/analyst/strategy），FK→auth.users |
| `advertisers` | PRD 6.1 拍平：kpi_mode/target_price/actual_price/achievement_rate + daily_budget/consume_speed + targeting(jsonb) + guaranteed_min_share（Tier1 校验 ≥0.30）+ 软删 + pg_trgm 模糊搜索 |
| `creatives` | 素材独立表：storage_path + status(testing/active/paused) + weight（A/B）+ 仅 paused 可删 |
| `ad_slots` | type + 频控三元组（daily_limit/interval_min/fatigue_window）+ guaranteed_enabled + ai_agent 配置 |
| `slot_fill_sources` | fillPriority 数组转关系表：source_type/advertiser_id/priority/weight/guaranteed_share/expected_ecpm/enabled；UNIQUE(slot_id, advertiser_id)；SUM(guaranteed_share)≤1 应用层校验 |
| `advertiser_daily_stats` | 每日快照（预算恢复点），PK(advertiser_id, stat_date)，UPSERT 目标 |
| `budget_ledger` | 扣费流水，event_id UNIQUE 幂等，按月分区 |
| `ad_events` | 曝光/点击，按月分区，event_id 幂等，30 天保留任务 |
| `conversions` | 转化独立表（+归因字段 attributed_click_id/ltv），≥180 天 |
| `ad_requests` | 5% 采样 + no_fill 全量，score_snapshot jsonb |
| `hourly_metrics` | 整点聚合（计数器快照 + 明细核对），保留 2 年 |
| `ai_decision_logs` | PRD 6.3 + manual_override/reverted/reverted_at |
| `ai_agent_config` | 单行表：optimization_goal/kpi_alert_threshold(0.85)/adjust_step(0.05)/learning_cycle/enabled |
| `config_change_audit` / `config_versions` | 配置审计（old/new jsonb）+ 缓存失效版本号 |

迁移工具：golang-migrate（纯 SQL 文件，`0001_init.sql` 起）。

## API 设计

**Open API（:8080，API Key + HMAC-SHA256 签名 + timestamp/nonce 防重放）**
- `POST /api/v1/ads/request` — 入参 `{slotKey, deviceId, appVersion, os, country, ts}`；出参 `{fill, advertiserId, creative:{type, mediaUrl(signed), durationMs}, requestId, fallback}`
- `POST /api/v1/events/batch` — `[{eventId, type:impression/click/conversion, requestId, advertiserId, creativeId, slotKey, deviceId, ts, attribution?}]`，客户端 30s/20 条/退后台触发；event_id 幂等；转化触发计费
- `GET /api/v1/config/slots` — 客户端配置快照（ETag 缓存）

**Admin API（:8081，Supabase Auth JWT（Go 用 JWKS 验 RS256）+ RBAC 中间件，不开 RLS——Go 是唯一写方）**
- 广告主：`GET/POST /advertisers`、`GET/PATCH/DELETE /:id`（软删）、`POST /:id/status`
- 素材：`POST /advertisers/:id/creatives`（元数据+storage path）、`PATCH /creatives/:id`、`DELETE /creatives/:id`
- 广告位：`GET/POST /slots`、`GET/PATCH /slots/:id`、`PUT /slots/:id/fill-sources`（事务整体替换）、`POST /slots/:id/ai-agent`
- 看板：`GET /dashboard/realtime`（内存计数器+环比）、`GET /dashboard/summary?range=`、`GET /dashboard/source-distribution`
- AI Agent：`GET/PATCH /ai-agent/config`、`GET /ai-agent/decisions`（筛选/导出 CSV）、`POST /ai-agent/decisions/:id/rollback`、`POST /:id/manual-override`
- 系统：`/healthz`、`/internal/metrics`（Prometheus）

素材上传流：前端创建元数据 → supabase-js 携 session 直传私有桶（50MB 视频不经 Go 中转）→ Go 签发 1h signed URL（防盗链）。

## 实施计划

### P0 核心链路（按依赖顺序）

1. **数据库**：`migrations/0001_init.sql` 全量 Schema（分区表 + NOTIFY 触发器 + pg_trgm）
2. **Go 骨架**：双端口 HTTP + Supabase JWT/JWKS 验证 + RBAC 中间件 + HMAC 中间件 + /healthz
3. **管理域**：广告主/素材/广告位/填充来源 CRUD + 审计日志 + ConfigSync 三通道
4. **决策引擎**：ConfigCache + ScoringEngine（公式单测）+ FrequencyStore + BudgetCtrl（含恢复）+ CreativeSelector + `/ads/request` 全流程
5. **上报链路**：`/events/batch` + 幂等 + 批写 + RealtimeCounters + 计费扣减
6. **前端 6 页**：/advertisers（列表/新增/详情）、/slots（列表/新增/详情含拖拽）+ 登录
7. **看板首页**：/dashboard/realtime 3s 轮询版
8. **部署验收**：Fly.io 上线 + vegeta/k6 压测 P99 <200ms

### P1 监控与预算平滑
预算平滑每小时任务（±10% 调 weight + 决策日志）→ /dashboard 完整版（KPI 卡片/广告主监控/饼图/下钻）→ /ai-agent 日志列表/筛选/导出 → 95% 预警 + 耗尽状态机 + Jakarta 0 点重置 → 聚合/保留任务 → Flutter SDK + 对接文档。

### P2 AI 规则引擎
三 Agent 自动化（KPI Guardian <85% 提权最高 2x / >120% 降权、Budget Controller 全自动、Exposure Optimizer 6h 学习周期）→ 决策回滚 → 接管流程（24h 学习期 + 模拟效果）→ 素材自动 A/B → Realtime 推送。

## 风险与应对

| # | 风险 | 应对 |
|---|------|------|
| 1 | 单实例单点 | Fly.io 自动重启 <10s 恢复（配置+预算快照加载）；热路径不查库使恢复极快；升级路径已隔离 |
| 2 | 预算 2s 异步落库超发窗口 | 损失有界（<数美元/广告主/崩溃）+ 95% 预警 + ledger 全量流水可对账 |
| 3 | Supabase Storage 视频出口流量费 | P0 监控带宽，超阈值迁 Cloudflare R2（storage_path 已抽象存储实现） |
| 4 | 转化归因延迟（点击→安装数小时）→ KPI 滞后 | 在途预估修正（曝光×预估 eCPM）+ 24h 归因窗口参数化 + 文档说明 KPI 曲线滞后特性 |
| 5 | LISTEN/NOTIFY 断连 | session pooler 固定 + 10s 版本轮询兜底 |
| 6 | 事件重试重复计费 | event_id 幂等（ledger UNIQUE + events 去重），SDK 负责重试语义 |
| 7 | DAU 远超 50 万假设 | 上线后用真实 QPS/内存水位验证；Redis/多实例触发条件写入 runbook |

## 验证方式

- **决策延迟**：Prometheus P50/P99 埋点 + vegeta/k6 压测验收 <100ms
- **决策正确性**：Go 单测覆盖打分公式、频控、疲劳、预算边界（95%/耗尽/次日恢复）
- **配置生效**：修改广告主配置后立即请求决策，验证毫秒级生效
- **端到端**：模拟客户端脚本 → 请求广告 → 上报曝光/点击/转化 → 验证预算扣减、KPI 计算、看板数据一致
- **前端**：本地 next dev + Go 本地实例联调 8 页交互（含拖拽优先级、实时刷新）
